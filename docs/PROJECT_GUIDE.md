# ShopPilot 项目完整讲解

这份文档回答三个问题：

1. 这个项目到底是什么，为什么不是“凭空写一个 Agent”？
2. 每个 Agent 能力在代码里怎样真正落地？
3. 面试时如何沿着业务链路讲清楚自己的技术判断？

建议先把项目跑起来，再按“演示 → 架构 → 关键代码 → 问答”的顺序阅读。

---

## 1. 一句话介绍

ShopPilot 是一个电商买卖双方共用的 Agent 演示平台：

- 买家输入自然语言，系统完成找货、比价、组合、算价和待确认订单草稿。
- 商家输入经营问题，系统沿漏斗定位异常、展示证据、生成可审批和可回滚的变更单。
- 模型只负责理解和表达；价格、库存、指标、权限、订单和写操作由服务端确定性代码负责。

项目采用“小闭环”而不是“大而全”的设计：只保留能证明 Agent 工程能力的最小流程，但每个关键环节都有真实数据、接口、状态、错误处理和测试。

---

## 2. 为什么这个项目适合面试展示

很多“Agent 项目”只在提示词里要求模型不要出错，但无法证明：

- 商品过滤是不是真的发生；
- 价格是不是模型随口算的；
- 模型会不会直接写数据库；
- 断线以后任务能不能恢复；
- 商家改价有没有审批和回滚；
- 模型调用失败有没有降级；
- 越权工具是不是会被拦住。

ShopPilot 对每条风险都给出代码级答案：

| 常见风险 | 项目回答 |
| --- | --- |
| 商品检索结果不可解释 | 返回关键词分、向量分、行为分、RRF 排名和过滤顺序 |
| 模型算错价格 | 价格由 `pricing.py` 固定函数计算，落单前再复算一次 |
| 模型直接下单 | 模型链路只能产生 `order_draft`，确认接口独立鉴权 |
| 重复点击造成重复订单 | 用户 + SKU 集合 + request_id 派生唯一幂等键 |
| 模型越权调用商家工具 | 14 个工具都声明 scope，网关按 JWT 角色拦截 |
| 经营指标口径不一致 | 指标定义、公式、数据源和时间粒度统一维护 |
| 商家动作无法撤销 | 执行前保存价格/库存/会员价快照，执行后支持回滚 |
| 模型服务不可用 | DS 不可用时自动切换确定性槽位解析 |
| SSE 断线丢结果 | 事件写入数据库，带自增事件编号，可按 `Last-Event-ID` 重放 |

## 3. 用户真正感知到的流程

### 3.1 买家侧示例

输入：

```text
预算 800 元，买一个 16 寸电脑通勤包和防晒霜，上海发货
```

系统行为：

1. 入口安全预检，检查提示注入和异常指令。
2. 确定性规则识别两个品类、800 元预算、16 寸、上海发货。
3. 先按预算、尺寸、库存和发货地过滤。
4. 对符合条件的商品做关键词召回和 Qdrant 向量召回。
5. 用 RRF 融合两路排名，再加入加购/支付行为分。
6. 只对完整商品组合运行固定算价函数。
7. 自动选择最合适的会员价和优惠券。
8. 生成“待确认订单草稿”，不直接落单。
9. 服务端再次检查 SKU、库存、价格和地址。
10. 用户点击确认后，再用幂等键创建订单。

演示结果：

- `BAG-16-BLK`：城市通勤 16 寸防泼水双肩包
- `SUN-50-MLD`：轻透防晒乳 SPF50+
- 商品小计：¥468
- 会员价节省：¥30
- 优惠券：会员满 199 减 50
- 最终应付：¥418

### 3.2 商家侧示例

看板显示近 7 日经营指标。系统将最近 2 天和之前 3 天比较，沿五个环节计算：

```text
曝光 → 点击 → 加购 → 支付 → 退款
```

演示数据中，`BAG-16-GRY` 的点击量下降约 52%，系统给出：

- 异常 SKU；
- 时间段；
- 当前日均与基线日均；
- 绝对差值和变化百分比；
- 样本量；
- 证据强度 `high / medium / low`；
- “模型不直接计算指标”的护栏说明。

随后可以对该 SKU 提出改价：

1. 系统读取当前价格、库存和近 7 日支付数据。
2. 计算影响 SKU 数量、库存风险金额和预计 GMV 变化。
3. 保存执行前快照。
4. 风险金额超过阈值时进入 `pending_approval`。
5. 审批后才能执行。
6. 执行会更新商品价格并记录审计日志。
7. 回滚从快照恢复价格、会员价和库存。

## 4. 总体架构

```text
浏览器
  │ REST + SSE
  ▼
FastAPI
  ├─ JWT / 角色校验
  ├─ 买家 Agent API
  ├─ 商家经营 API
  └─ 14 工具 REST 代理
       │
       ├─ LangGraph Buyer Workflow
       │    ├─ guard
       │    ├─ understand
       │    ├─ retrieve
       │    ├─ price
       │    ├─ draft
       │    └─ validate
       │
       ├─ Merchant Service
       │    ├─ metrics semantic layer
       │    ├─ funnel diagnosis
       │    ├─ change order
       │    ├─ experiment report
       │    └─ audit / rollback
       │
       ├─ Tool Gateway
       │    ├─ JSON Schema
       │    ├─ role scope
       │    ├─ timeout / retry
       │    └─ error mapping
       │
       └─ FastMCP HTTP

数据层
  ├─ MySQL：商品、草稿、订单、会话、变更、审计
  ├─ Redis：热上下文和缓存，本地自动回退为内存
  └─ Qdrant：商品向量召回，未配置时自动回退为本地关键词
```

### 4.1 为什么用单体演示

真实系统里可以拆分商品服务、订单服务和 Agent 服务，但面试 Demo 的重点是证明业务闭环和工程边界，而不是堆十几个微服务。

当前单体保留了服务边界：

- 工具网关是统一入口；
- 买家工作流与商家经营逻辑分模块；
- 订单、商品、行为事件、变更单和审计各有独立模型；
- Docker Compose 中 MCP 服务独立进程；
- 数据源按生产形态接入 MySQL、Redis 和 Qdrant。

面试时可以明确说：“我在演示中用模块化单体降低运行成本，但保留了可拆分边界。生产上会按读写压力将商品检索、订单写入和 MCP 网关独立部署。”

## 5. 买家 Agent 的六个节点

代码入口：`app/buyer_service.py`。

### 5.1 guard：安全预检

目标：

- 拦截“忽略之前指令”“泄露系统提示”“绕过校验”等提示注入；
- 在进入模型和工具前做第一层拦截；
- 控制过长输入。

实现：

- 正则规则匹配 `PROMPT_INJECTION_PATTERNS`；
- 命中后任务状态变为 `blocked`；
- 返回固定错误码 `PROMPT_INJECTION`；
- 不继续检索、不调用工具、不生成草稿。

面试表达：

> 我不会把“不要听用户越界要求”完全交给模型遵守。入口先用规则拦高频风险，模型之后还会受到工具 scope 和服务端写操作校验约束，是多层防御。

### 5.2 understand：槽位抽取

确定性规则先提取：

- 品类；
- 预算；
- 笔记本尺寸；
- 场景；
- 城市；
- 会员身份。

如果配置了 DeepSeek：

- 模型通过 OpenAI-compatible `/chat/completions` 返回 JSON；
- 规则已有值不会被模型覆盖；
- 模型只补缺失语义；
- 连续失败后使用本地解析结果。

为什么这样做：

- 预算和尺寸是硬条件，不能让模型猜；
- 规则便宜、稳定、可测试；
- 模型只解决“通勤、轻便、送礼”等非结构化语义。

### 5.3 retrieve：约束标签和混合检索

先做硬过滤：

1. 是否在目标类目；
2. 是否有库存；
3. 会员/非会员价格是否超预算；
4. 是否满足发货城市；
5. 是否满足 16 寸等尺寸条件。

再做两路召回：

- 关键词召回：商品名、标签、描述、富文本属性；
- 向量召回：将商品结构化属性拼接后生成向量，通过 Qdrant 查询。

本地没有 Qdrant 时：

- 系统仍执行关键词和行为重排；
- 健康接口明确显示 `vector: disabled`；
- 不会假装向量检索成功。

融合：

```text
RRF 分数 = 1 / (60 + 关键词排名) + 1 / (60 + 向量排名)
```

之后叠加少量加购和支付行为分，避免只命中文字但历史转化很差的商品排到前面。

### 5.4 price：确定性组合与算价

代码：`app/pricing.py`。

价格职责：

- 会员价与普通价选择；
- 优惠券门槛判断；
- 自动选择优惠力度最大的可用券；
- 上界预算内选择完整商品组合；
- 输出商品行、小计、会员节省、券优惠和总价。

模型不参与：

- 乘除计算；
- 预算是否超限；
- 优惠券是否可用；
- 最终金额。

### 5.5 draft：待确认草稿

写入 `OrderDraft`：

- 关联 Agent run；
- 保存商品与价格快照；
- 状态固定为 `pending_confirmation`；
- 前端通过 UI Schema 获得“确认订单”“调整条件”动作。

关键点：

> 草稿不是订单。即使模型输出漂亮，也不会触发真实支付或订单状态。

### 5.6 validate：后置校验

服务端重新：

- 读取商品；
- 检查是否下架；
- 检查库存；
- 重新算价；
- 与草稿金额比较。

任何不一致都返回 `validation_failed`，要求重新生成方案。

### 5.7 确认订单：第二道写操作保护

确认接口再次执行：

1. 草稿归属校验；
2. 草稿状态校验；
3. SKU 存在；
4. 商品可用；
5. 价格复算；
6. 高金额凭证校验；
7. 单笔上限校验；
8. 幂等键查询；
9. 创建订单；
10. 唯一键冲突时返回已存在订单。

幂等键：

```text
sha256(user_id | sorted(SKU set) | request_id)
```

这保证同一用户的同一请求重复提交不会生成多笔订单。

## 6. 商家 Agent 的闭环

代码入口：`app/merchant_service.py`。

### 6.1 指标语义层

当前统一了六个指标：

| 指标 | 公式 | 数据源 |
| --- | --- | --- |
| GMV | `SUM(pay.amount)` | 交易库 |
| UV | `SUM(impression)` 去重近似 | 买家行为回流 |
| 支付转化率 | `SUM(pay.count) / SUM(impression.count)` | 交易库 + 行为 |
| 退款率 | `SUM(refund.count) / SUM(pay.count)` | 售后库 |
| 加购率 | `SUM(add_cart.count) / SUM(click.count)` | 买家行为回流 |
| 客单价 | `GMV / SUM(pay.count)` | 交易库 |

每个指标带：

- 名称；
- 公式；
- 粒度；
- 数据源；
- 口径备注。

面试价值：

> 指标语义层解决的是“每个人都在算，但每个人算得不一样”的问题。Agent 不能自己写 SQL 或猜口径，只能消费语义层输出。

### 6.2 漏斗诊断

对于每个 SKU 和每个阶段：

```text
当前日均 = 最近 2 天事件量 / 2
基线日均 = 之前 3 天事件量 / 3
变化率 = (当前日均 - 基线日均) / 基线日均
```

系统选择变化最明显的环节，返回：

- SKU；
- 商品名；
- 环节；
- 当前/基线日均；
- 绝对变化；
- 百分比变化；
- 样本量；
- 证据强度。

当样本不足时返回 `insufficient_evidence`，而不是强行给结论。

### 6.3 变更单

变更单包含：

- 动作类型；
- 目标 SKU；
- 新参数；
- 执行前快照；
- 影响 SKU 数量；
- 风险库存；
- 风险金额；
- 基线日均订单；
- 预计 GMV 变化；
- 是否需审批；
- 创建人、执行时间和回滚时间。

状态流转：

```text
pending_approval → approved → executed → rolled_back
```

风险判断：

- 风险金额超过 `APPROVAL_THRESHOLD_CENTS` 时必须有审批；
- 未审批直接执行返回 `APPROVAL_REQUIRED`；
- 回滚只能针对已执行变更；
- 执行与回滚都写审计日志。

### 6.4 效果回测

实验记录两组样本：

- 对照组访问与转化；
- 实验组访问与转化；
- 退款率变化。

系统计算：

- 两组转化率；
- 相对提升；
- 标准误；
- Z 分数；
- 近似置信度；
- 决策：继续观察或收集更多数据。

这部分用于表达“上线不是结束，效果验证才是闭环”。

## 9. SSE、断线续传与会话记忆

### 9.1 SSE 实现

前端提交任务后：

1. `POST /api/buyer/runs` 返回 `run_id`；
2. 前端打开 `GET /api/buyer/runs/{run_id}/events?token=...`；
3. 服务端从 `RunEvent` 表读取已发生事件；
4. 每条事件带 `id`、`event` 和 `data`；
5. 空闲时发送注释心跳；
6. 完成后发送 `run.completed` 并关闭。

### 9.2 断线续传

浏览器重连时自动携带 `Last-Event-ID`：

- 服务端解析最后序号；
- 只返回更大的事件；
- 已完成的步骤不会让前端重新显示一遍；
- 即使任务在响应发出前已经完成，也能从数据库重放。

### 9.3 会话记忆

- 每轮用户和助手消息写入 `Conversation`；
- Redis 可用于热上下文；
- 本地无 Redis 时自动退回进程内存；
- 写库前使用 `mask_pii` 脱敏手机号、邮箱和身份证；
- 超过 6 条 turns 后压缩较早对话为摘要，只保留最近 4 条。

### 9.4 任务快照续跑

除 LangGraph checkpointer 外，每个节点结束后都会把 `current_step` 和完整业务状态写入
`AgentRun.state`。如果进程中断，可以调用：

```http
POST /api/buyer/runs/{run_id}/resume
```

新增的 `resume_router` 会读取最后一个已完成节点，从下一个节点继续。例如：

```text
understand 已完成 → 从 retrieve 继续
price 已完成 → 从 draft 继续
draft 已完成 → 从 validate 继续
```

续跑前会写 `run.resumed` SSE 事件，续跑后仍走同样的校验和终态处理。

## 10. 安全设计

### 10.1 角色权限

- 买家只能调用买家 API 和买家工具；
- 商家只能调用经营 API 和经营工具；
- JWT 中包含 `sub`、`role`、过期时间和 issuer；
- 工具网关再次检查 scope，不信任前端传来的角色。

### 10.2 写操作保护

- 草稿不直接落单；
- 确认接口重新校验；
- 高金额订单要求在服务端验证凭证；
- 支付凭证不进入模型上下文；
- 退款、改地址、代下单需二次确认；
- 高风险售后统一转人工复核；
- 商家变更单有审批阈值；
- 执行与回滚都有审计。

### 10.3 输出护栏

- 硬约束由规则层处理；
- 检索无结果时主动要求放宽条件；
- 价格不一致时拒绝确认；
- 样本不足时拒绝形成高置信度经营结论；
- 模型调用异常时切换规则兜底。

- 生产 Compose 再切换到 MySQL、Redis、Qdrant。

## 14. 可能的追问与回答

### 为什么不用 Agent 直接生成 SQL？

> 经营指标必须有稳定口径。模型生成 SQL 容易越权、扫描大表、口径漂移。我的设计是模型调用
> `merchant.metrics` 工具，工具内部走白名单指标语义层。真实生产还需要 SQLGlot AST
> 二次校验、只读账号、行数限制和超时，这部分在简历项目里做过，演示版裁剪了。

### 为什么价格不交给模型？

> 价格是强一致业务。模型适合理解“预算不高、通勤用”，不适合执行满减、券门槛和组合约束。
> 因此我用固定函数，并在草稿确认时重新计算，防止缓存或模型输出价差。

### LangGraph 在这里有什么用？

> 它让节点职责和状态明确。安全、理解、检索、算价、草稿、校验都可以单独观测。
> 每一步会写 AgentRun 快照和 SSE 事件，后续可以替换成持久化 checkpointer，支持进程重启后恢复。

### SSE 如何保证断线后不重复？

> 事件先落库并分配自增 sequence。浏览器重连带 `Last-Event-ID`，服务端只补序号更大的事件。
> 前端不是依赖某一次 HTTP 连接的内存流。

### 模型挂了怎么办？

> 槽位解析可以退回确定性规则。硬约束本来就走规则，价格与库存也不依赖模型。
> 多模型 failover 在 `llm.py` 支持按配置逐个尝试，记录失败后降级。

### 幂等键重复但内容不同怎么办？

> 当前幂等键包含用户、SKU 集合和 request_id，重复提交返回原订单。生产上还会把地址与价格版本
> 纳入 canary hash，并保存请求摘要；同 key 不同 body 返回幂等冲突，而不是悄悄覆盖。

### 为什么变更单需要回滚快照？

> 经营动作会影响用户可见价格和商家收入。执行前保存完整 before snapshot，回滚时恢复原值，
> 同时写审计日志。这样即使短期实验失败，也能在分钟级恢复，而不是靠人工查旧值。

### 为什么选这两个场景？

> 买家侧证明长任务、工具调用、检索、写操作防护和流式交互；商家侧证明指标口径、归因、
> 审批和回滚。两者共用商品和订单主数据，又恰好覆盖 Agent 在“建议型”和“执行型”场景中的差别。
